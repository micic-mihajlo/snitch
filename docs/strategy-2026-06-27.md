# Snitch Strategy Deep Dive

Date: 2026-06-27
Status: Recommended next build direction

## Executive Take

Snitch should become the **live verification layer for AI coding agents**.

The strongest product move is not to compete head-on with PR reviewers. CodeRabbit, Greptile, Graphite Diamond, Sourcegraph, and CodeSee already cover parts of the post-change review surface. Snitch is sharper if it moves earlier:

> The agent is still writing code. Snitch is already showing what changed, what got riskier, and what companion work is missing.

That means the next build should focus on:

1. installable background adapters for Codex, Claude Code, and OpenCode
2. deterministic TypeScript extraction from real repo files
3. live graph deltas plus a timeline/trace of the agent run
4. fast semantic narration and missing-companion checks via Cerebras
5. repo memory and false-positive learning via Backboard
6. PR-ready artifacts as the durable output, not the core identity

## Market Signal

The 2025-2026 developer tooling market is converging on one pain: AI made code generation fast, but verification did not scale.

Useful research anchors:

- Stack Overflow 2025 reports high AI adoption but low trust: 66% of developers are frustrated by AI output that is "almost right", and 45.2% say debugging AI-generated code is more time-consuming.
- Sonar's 2026 State of Code survey reports a verification bottleneck: developers estimate 42% of committed code is AI-generated/assisted, 96% do not fully trust AI-generated code, and only 48% always check AI-assisted code before committing.
- GitLab's 2026 AI Accountability research says 85% agree AI moved the bottleneck from writing code to reviewing/validating it, while 92% report governance challenges with AI-generated code.
- New Relic's 2026 State of AI Coding report frames this as production reliability: leaders rate AI code highly during review, yet report more incidents and rework once it ships.

Positioning should avoid generic "AI code review" language.

Better:

- AI made code cheap. Trust is still expensive.
- Snitch verifies agent-written code while the agent is still writing it.
- Catch the plausible-but-wrong changes before they become review debt.
- Live system maps for AI-generated changes.

## Competitive Read

### CodeRabbit

Strong at PR/IDE/CLI review, learned team rules, and pre-commit style feedback.

What to copy:

- local/uncommitted review loop
- team-rule ingestion from repo instruction files
- actionable fixes instead of generic comments

What not to copy:

- becoming another comment generator
- trying to own every static-analysis category

### Greptile

Strong at repo graph context, impact-aware review, PR diagrams, and test-generation direction.

What to copy:

- graph-backed review explanations
- "who calls this / what breaks / what changed downstream"
- cross-file impact as first-class product value

What not to copy:

- waiting until PR time to show the graph
- hiding the graph as backend context only

### Sourcegraph

Strongest context substrate: search, code navigation, definitions, refs, ownership, history, multi-repo context.

What to copy:

- navigable evidence
- definitions/usages as first-class drilldowns
- retrieval transparency

What not to copy:

- trying to become a full code intelligence platform during the hackathon

### Graphite / Diamond

Strong workflow framing: stacked changes, dependency-aware PRs, fewer higher-signal comments.

What to copy:

- dependency-aware change chunks
- visual change ordering
- low-noise defaults

What not to copy:

- tying Snitch to one PR workflow

### CodeSee / Nx / Sentry

CodeSee and Nx show that visual review works when the user can narrow scope. Sentry shows the best causality pattern: waterfall, trace, drilldown, related evidence.

What to copy:

- scoped graph views instead of one giant map
- timeline/trace UI for agent activity
- expand from summary to exact evidence

## Product Direction

Snitch should have three modes:

### 1. Live Mode

The hackathon wow.

Input:

- agent hooks
- file watcher
- replay script fallback

Output:

- graph deltas
- timeline of agent events
- fast narration
- missing companion warnings
- repair prompts

The demo should show a coding agent adding a capability and Snitch immediately revealing the system impact: new tool, schema, external API, env var, missing audit trail, missing permission boundary, missing unauthorized-call test.

### 2. Evidence Mode

The daily-use product.

Input:

- current graph
- base graph
- task intent
- repo rules
- agent event trace

Output:

- "what changed structurally"
- "what contract changed"
- "what companion work is missing"
- "why this warning exists"
- links to exact files/lines
- copyable repair prompt

### 3. Publish Mode

The durable artifact.

Input:

- graph snapshot
- timeline
- warnings
- evidence references

Output:

- `.snitch/pr-comment.md`
- `.snitch/mermaid.mmd`
- `.snitch/handoff.md`
- optional GitHub Action comment
- optional 8090 work-order status/handoff

This plane should not require the coding agent to hold GitHub write permissions.

## Hook Reality

The background-companion direction is technically realistic.

### Codex

OpenAI Codex hooks support a project-local hook configuration and lifecycle events including `PreToolUse`, `PostToolUse`, `Stop`, `SessionStart`, `SessionEnd`, notifications, compaction, and plugin-bundled hooks.

Recommendation:

- Make Codex the first-class demo adapter.
- Generate `.codex/hooks/snitch.json` or an equivalent project hook config from `snitch init`.
- Use `PostToolUse` and `Stop` first.
- Add `PreToolUse` later for blocking or preflight warnings.

### Claude Code

Claude Code has mature command/http/prompt/agent hooks, async/background hooks, project/user/plugin locations, and events such as `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolBatch`, `Stop`, and `SessionEnd`.

Recommendation:

- Generate `.claude/settings.local.json` for local setup.
- Use command hooks first.
- Add HTTP hooks once `snitchd` exists.
- Package a plugin later if the demo has time.

### OpenCode

OpenCode plugins expose file, command, session, permission, shell, and tool events such as `file.edited`, `file.watcher.updated`, `session.diff`, `tool.execute.before`, and `tool.execute.after`.

Recommendation:

- Add an OpenCode plugin adapter after Codex/Claude.
- Prefer `file.edited` and `tool.execute.after` for Snitch.
- Keep the normalized event schema runtime-agnostic.

### GitHub

GitHub Actions `pull_request` events are the right publish plane. PR comments use the issue comments API because every PR is also an issue.

Recommendation:

- Do not add GitHub MCP to the core demo.
- Add a workflow template that runs `snitch finalize` and posts/updates one top-level Snitch comment.

## Technical Direction

### Graph Truth

Use deterministic extraction as the source of truth. LLMs can label, rank, narrate, and infer missing companions, but they should not invent graph nodes.

Recommended extraction stack:

- MVP: `ts-morph` over the TypeScript compiler API
- Optional module graph shortcut: `dependency-cruiser`
- Later dirty-buffer/polyglot support: Tree-sitter
- Later security/policy enrichers: Semgrep or CodeQL
- Nx/Turborepo graph only when already present in the repo

Immediate extractor passes:

1. package/workspace nodes from `package.json`
2. file/module nodes from TS source files
3. exported function/class/type/interface symbols
4. imports and re-exports
5. Next.js/server route handlers
6. Zod schemas
7. tool registry entries
8. `process.env.*` references
9. `fetch()` and SDK client calls
10. test files and coverage edges by naming/import proximity

Important graph rules:

- stable IDs are mandatory
- source evidence must include file and line
- type-only edges and runtime edges should be separate
- unresolved references should be preserved with lower confidence, not dropped
- last valid parse state should stay visible during broken edits

### Event Model

Model the agent run as spans, not just events.

Suggested event shape:

```ts
type SnitchEvent = {
  id: string;
  runId: string;
  parentId?: string;
  source: "codex" | "claude" | "opencode" | "git" | "watcher" | "replay";
  phase:
    | "session_start"
    | "prompt"
    | "tool_before"
    | "tool_after"
    | "file_changed"
    | "graph_updated"
    | "warning_created"
    | "repair_prompt_created"
    | "session_stop";
  receivedAt: string;
  payloadHash: string;
  safeSummary: Record<string, string | number | boolean>;
  evidence?: Array<{ file: string; line?: number; symbolId?: string }>;
};
```

This lets the UI become a trace:

- prompt
- tool call
- file edit
- graph delta
- warning
- repair prompt

That is more distinctive than a static graph.

### UI Direction

Keep React Flow for the demo/live surface.

Add:

- structural fingerprinting so layout does not rerun for cosmetic changes
- position cache keyed by graph node ID
- animated deltas: node added, edge added, warning attached, companion repaired
- trace rail beside the graph
- "why" drawer for each warning with exact evidence
- scoped views: changed-only, impacted neighborhood, all graph

Use Mermaid only for export/docs/PR comments.

Use ELK later for layout quality, but do not let layout computation block live updates. Run layout asynchronously and discard stale layout results.

## Sponsor Architecture

### Cerebras

Cerebras should be load-bearing in the demo. The pitch is speed-of-meaning.

Use it for:

- one-line graph-diff narration
- missing companion ranking
- repair prompt generation
- PR/handoff summary wording
- structured JSON classification of graph deltas

Use fast short calls synchronously. For longer handoff text, stream or run after the graph update.

Critical rule:

- Cerebras never owns graph truth.
- Cerebras consumes graph diff + evidence and returns labels, warnings, repair prompts, summaries.

### Backboard

Backboard should be repo memory, not live graph truth.

Use it for:

- accepted repo rules
- "this warning was false positive because..."
- prior session handoff retrieval
- team conventions
- sponsor-visible persistent memory lane

Safe MVP approach:

- store only concise memory facts and evidence hashes
- use `Readonly` retrieval during live warnings
- write memory on explicit finalization or accepted feedback

### 8090 Software Factory

8090 should be an adapter, not the identity.

Use it for:

- import Work Order as task intent
- read linked requirements/blueprints
- export Snitch handoff/status

Do not make Snitch feel like an 8090-only tool. The message is:

> Snitch works for any prompt, issue, ticket, or work order. 8090 Work Orders are just a richer intent source.

## Concrete Build Order

### Implemented First Slice

The repo now has the first build-out slice:

- `packages/events` normalizes hook events into trace phases and stores safe summaries, hashes, and file evidence.
- `packages/cli` supports `snitch init --agent codex|claude|opencode|all` and emits Codex, Claude Code, and OpenCode adapter files.
- `packages/cli` supports `snitch analyze --target <repo>` to run a code-derived TypeScript graph extraction.
- `packages/cli` persists the analysis target and refreshes code-derived artifacts after file-changing hook events.
- `packages/cli` supports `snitch watch` to serve `.snitch` artifacts over local HTTP and SSE.
- `packages/extractor-ts` uses `ts-morph` to extract the prepared demo app's assistant router, tool registry, issue tool, schema, provider API, env var, and missing companion warnings.
- `apps/web` polls the local live server and falls back to replay when it is not running.
- `apps/demo-app` is a prepared TypeScript coding-assistant target for live/replay demos.
- `pnpm demo:extract` writes `.snitch` artifacts from the extractor path.

## Demo Script

Start with Snitch already running:

```bash
pnpm snitch init --agent codex --task "Add an external issue-creation tool"
pnpm snitch watch
pnpm dev
```

Then show:

1. Agent begins editing `apps/demo-app`.
2. Snitch trace rail shows tool/file events.
3. Graph adds `IssueTool`, `CreateIssueInput`, `IssueProviderAPI`, and `ISSUE_PROVIDER_API_KEY`.
4. Cerebras narration appears instantly: "External issue creation capability added; provider credential now in path."
5. Snitch warning nodes appear: no audit, no redaction, no permission scope, no unauthorized-call test.
6. Click warning.
7. Repair prompt appears.
8. Agent applies repair.
9. Graph warnings disappear as audit/redaction/permission/test nodes appear.
10. `snitch finalize` writes PR-ready Mermaid and Markdown.

The line for judges:

> The agent said it was done. Snitch showed what the system actually became.

## Risks

- If extraction is fake, the project feels like a dashboard toy. Ship a real narrow extractor even if it only handles the demo app.
- If the graph is too broad, users will not read it. Default to changed neighborhood.
- If warnings are generic, it becomes another reviewer. Warnings must cite graph evidence and missing companion logic.
- If sponsor integrations are decorative, judges will notice. Cerebras must visibly make the semantic loop fast; Backboard must visibly remember repo rules or warning feedback.
- If the agent needs GitHub write permission, the security story weakens. Keep publishing separate.

## Recommendation

Build toward this sentence:

> Snitch is the local black box recorder and live system map for AI coding agents.

For the hackathon, the best next slice is:

- real `ts-morph` extractor
- Codex/Claude hook config generation
- live event trace
- graph delta narration through Cerebras
- Backboard-backed repo rule memory

That turns Snitch from "cool graph of code" into "the thing you add to your coding agent so it cannot silently ship weird system changes."
